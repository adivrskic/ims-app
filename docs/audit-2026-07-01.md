# Nimbus / Nautilus WMS — Audit & Bug Report

**Date:** 2026-07-01
**Scope:** Full codebase (`D:\app-nimbus1`, Next.js 15 + Supabase), live database (`nimbus-wms` = `seypbrzjjiuibrwyxewj`), security, correctness, unfinished work.
**Method:** Multi-agent code sweep (security/correctness + unfinished-work), live Supabase advisors (security + performance), direct DB inspection, `tsc --noEmit` + `next build` verification. Read-only except where noted.

---

## Executive summary

The app is production-shaped and disciplined on the fundamentals: RBAC gates essentially every mutation, RLS is enabled with policies on all `app` tables, the service-role admin client always filters by `org_id`, and the core stock-mutating operations run in advisory-locked/drift-guarded Postgres RPCs.

This cycle closed the entire prior audit (truncation-driven oversell, allocation races, open redirect, CSV injection, QC ordering, cycle-count atomicity, legacy-schema exposure, dead code). A **fresh** sweep afterward surfaced a small set of **new** issues — most notably an **authenticated SSRF via the outbound-webhook feature (High)** and two ungated server actions — plus a couple of truncation/injection spots the first pass missed. None are Critical. They are listed in [Part B](#part-b--open-findings-new-this-audit).

### 🟠 High (found & fixed in the cleanup pass — commit `cbf3115`)

**H2 — Cross-org inventory leak via `app.inventory_list`.** The RPC is `SECURITY DEFINER` (bypasses RLS) and filters by the caller-supplied `p_org` with no membership check, yet `anon`/`authenticated` held `EXECUTE` (inherited via `PUBLIC`). Anyone with the public anon key could `POST /rest/v1/rpc/inventory_list { p_org: <any-org-id> }` and read that org's entire inventory (names, SKUs, on-hand, locations). The app only ever calls it — and `snapshot_inventory` — through the service-role admin client, so the fix revokes `EXECUTE` from `PUBLIC`/`anon`/`authenticated` (keeping `service_role`). Migration `20260702120000_lock_down_definer_rpcs.sql`; verified `anon`/`authenticated` EXECUTE now false.

### 🔴 Critical
None.

### 🟠 High

**H1 — Authenticated SSRF via outbound webhook endpoints.**
`createWebhookEndpoint` accepts any `https://` URL with no host restriction (only scheme + `new URL()` parse), stores it, and `deliverWebhook` then POSTs to it server-side and **persists the response body** (truncated) into `webhook_deliveries`, readable by the org via `getRecentDeliveries` / returned by `testWebhookEndpoint`. An org admin can point an endpoint at `http(s)://169.254.169.254/…` (cloud metadata), `localhost`, or internal hosts and exfiltrate the response — classic SSRF with response reflection. (Slack/Shopify senders are host-locked; this generic endpoint is the vector.)
- `lib/integrations/webhooks.ts:135` (`deliverWebhook` → `fetch`), `app/(app)/integrations/webhooks/actions.ts:27` (`createWebhookEndpoint`)
- **Fix:** after parsing, reject non-public destinations — resolve the host and block RFC-1918 / loopback / link-local / ULA / metadata IPs; disable redirect following (or re-validate the redirect target); allowlist port 443; re-validate at delivery time, not just creation.

### 🟡 Medium

**M1 — `revokeInvite` missing its permission gate.** Unlike `inviteMember` (gated on `members.manage`), `revokeInvite` only checks sign-in — any plain member can delete any pending invite in the org.
- `app/(app)/settings/actions.ts:88` — **Fix:** add `if (!ctx.can("members.manage")) return;`

**M2 — `testWebhookEndpoint` missing its permission gate.** Create/update/toggle/delete gate on `integrations.manage`; `testWebhookEndpoint` only checks sign-in, so any member can drive a server-side fetch to a stored endpoint (widens who can exercise H1).
- `app/(app)/integrations/webhooks/actions.ts:163` — **Fix:** add `if (!ctx.can("integrations.manage")) …`

**M3 — Purchase-orders list count/total truncates at 1000 rows.** Same bug class the truncation pass fixed elsewhere, missed here: neither the list nor the counts query paginates or uses a head-count, so status counts and `total` are wrong past 1000 POs and the list truncates.
- `lib/data/purchaseOrders.ts:63-87` — **Fix:** `{ count:"exact", head:true }` for counts; `fetchAllPaged` (or explicit range + "N of M") for the list.

**M4 — Orders CSV export lacks formula-injection neutralization.** Sibling of L1: `csvCell` here quotes for structure but does not prefix `= + - @` cells (customer name/notes are user-controlled). Also, unlike the other export routes it never resolves org context — it relies entirely on RLS (safe today, but inconsistent/defense-in-depth gap).
- `app/(app)/api/orders/export/route.ts:14-20` — **Fix:** copy the `/^[=+\-@\t\r]/` guard from the inventory/reports/valuation exports; optionally add an explicit `org_id` filter.

### 🟢 Low

- **L1 — `lookupBarcode` uses `.maybeSingle()` without org filter.** RLS scopes to org (no leak), but two same-org products sharing a barcode throw instead of returning "not found." `app/(app)/scan/actions.ts:51-64`.
- **L2 — Non-atomic provisioning flows leave orphans on partial failure.** org→profile→membership→facility as separate admin writes. `app/(app)/actions.ts:106`, `app/(app)/workspaces/new/actions.ts:56`, `app/admin/onboard/actions.ts:42`. A `SECURITY DEFINER` function would make them transactional.
- **L3 — `receiveLineItem` read-modify-write on `quantity_received` is non-atomic.** Concurrent receipts on one line can lose an update. `app/(app)/purchase-orders/actions.ts:329-358`. Low (putaway model; not a hotspot).
- **L4 — `placeLocation` / `buildWave` don't re-validate client-supplied `section_id`/`warehouse_id` against the org before insert.** Self-inflicted only (reads stay org-scoped); add a `.eq("org_id", ctx.orgId)` existence check. `facilities/[id]/sections/[sectionId]/actions.ts:193`, `picking/actions.ts:26-58`.
- **L5 — `lib/supabase/admin.ts` lacks `import "server-only"`.** Relies on "use server" tree-shaking; add the guard for a build-time safety net.

## Part C — Database advisor state (live)

### Security (62 lints; 1 ERROR)
- **ERROR ×1 — `security_definer_view`: `public.article_feedback_summary`.** Marketing-site aggregate view runs as owner, bypassing RLS. Low data risk (aggregate feedback counts only), but flipping to `security_invoker` would break the marketing display unless an anon aggregate-read policy is added first. **Product decision (marketing app).**
- **WARN ×16 — `function_search_path_mutable`.** All `public.*` legacy/marketing helper functions; every `app.*` function (incl. the RPCs added this cycle) already pins `search_path`. Low value now that legacy tables are quarantined.
- **WARN ×32 — SECURITY DEFINER functions executable by `anon`/`authenticated`** (16 each). Mostly intentional RPCs; review and `REVOKE EXECUTE FROM anon` on any that shouldn't be public.
- **WARN ×3 — `extension_in_public`** (`pg_trgm`, `vector`, `pg_net`). Moving them risks breaking marketing embeddings/edge — leave unless coordinated.
- **WARN ×1 — `auth_leaked_password_protection` disabled.** Enable the HaveIBeenPwned check in Auth settings (one dashboard toggle).
- **INFO ×9 — `rls_enabled_no_policy`.** All default-deny/safe (`app.user_sessions` + marketing tables).
- Distribution: 52 lints on `public` (marketing + legacy helpers), 9 on `app`.

### Performance (315 lints; all WARN/INFO)
- **144 × `multiple_permissive_policies`** — mostly on `app` tables by design (separate read + write RLS policies for the same role/action) + the quarantined legacy tables. Minor.
- **123 × `unused_index`, 40 × `unindexed_foreign_keys`** — premature at current data volume; worth an index pass before scaling (e.g. `asn_lines_po_line_id_fkey` lacks a covering index).
- **7 × `auth_rls_initplan`** — policies re-evaluate `auth.<fn>()` per row; wrap as `(select auth.uid())`. Mostly legacy tables.
- **1 × `auth_db_connections_absolute`** — Auth server capped at 10 connections; switch to percentage-based before bumping instance size.

> Note: quarantining the legacy tables to a `legacy` schema **de-exposed** them from the REST API but did **not** reduce the lint count — the lints moved with the tables. A future `drop schema legacy cascade` clears the ~69 legacy-schema lints in one shot.
