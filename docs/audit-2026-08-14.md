# Audit — security, performance, UX & docs (2026-08-14)

Full-codebase sweep of the dashboard at `main` (`ac6d7d0`). Scope: security posture,
vulnerabilities, performance / Core Web Vitals, UX, bugs, and documentation currency.

**Baseline at start:** 77 tests passing, `npm run build` clean.
**Baseline at end:** 88 tests passing, `npm run build` clean, bundle unchanged (102 kB shared).

Severity: **P0** = exploitable / data corruption · **P1** = correctness · **P2** = quality, perf, hardening · **P3** = polish.

## Fixed in this pass

### P1 — No security headers anywhere · `next.config.mjs`

The app shipped with **no CSP, HSTS, `X-Frame-Options`, `X-Content-Type-Options`,
`Referrer-Policy` or `Permissions-Policy`** — nothing in `next.config.mjs`, and no
`netlify.toml` / `vercel.json` / `_headers` to supply them at the edge. The app was
framable (clickjacking against destructive actions like *Cancel order* or *Void count*)
and had no script/connect restriction at all.

**Fixed:** a `headers()` block emits all six on every route. Notes for whoever touches it:

- `script-src` keeps `'unsafe-inline'` **by design** for the pre-hydration theme script.
  Adding a nonce or hash alongside it makes browsers *ignore* `'unsafe-inline'` (CSP3) and
  breaks every other inline script. Go full-nonce or leave it — not halfway.
- `style-src` needs `'unsafe-inline'`: ~900 inline `style={{…}}` props plus Tailwind.
- `connect-src` is derived from `NEXT_PUBLIC_SUPABASE_URL` and includes the `wss:` form —
  without it, Realtime dies silently and dashboards go stale with no error.
- `'unsafe-eval'` is dev-only (React Refresh). Verified the three.js/drei/fiber stack
  contains no `eval` / `new Function`, so the 3D viewer is safe under the production policy.
- HSTS is production-only — it's a one-way door on a custom domain.

**Verified:** headers present via `curl -I`; login page renders with zero console errors,
theme script executes, Satoshi + JetBrains Mono load.

### P1 — Forecast "Apply" silently did nothing for most members · `analytics/forecast/actions.ts`

`applyForecastSettings` writes `products.reorder_point` / `safety_stock` but carried **no
permission check**, unlike every other product write. The RLS `products_update` policy
requires `inventory.manage`, so for a member without it the write was rejected — and the
action ignored the error and revalidated anyway. The user saw the page reload with the old
numbers, no error, no explanation. Reachable from two places (the forecast worklist and
every product detail page).

**Fixed:** added the `inventory.manage` gate to the action, and gated the button on both
call sites so it isn't offered to people who can't use it.

### P1 — Divergent CSV encoders corrupted numeric export columns · 4 export routes

`csvCell` had been copy-pasted into all four export routes and drifted apart in two ways:

1. **Reports + valuation exports quoted negative numbers.** `-1234.56` was emitted as
   `'-1234.56`, which Excel/Sheets treat as *text* — so it drops out of `SUM()`. That hit
   exactly the two exports full of negative variances and adjustments. Inventory and orders
   had the numeric-preserving guard; these two didn't.
2. **Inventory + orders omitted `\r` from the quote trigger.** A value containing a bare
   carriage return broke row framing in the emitted file.

All four *did* correctly defend against formula injection (`=`, `+`, `-`, `@`, tab, CR) —
that part was fine everywhere.

**Fixed:** one shared `lib/print/csv.ts` with both bugs fixed, all four routes switched to
it, and **11 regression tests** (`test/csv.test.ts`) locking down injection handling,
numeric preservation, and RFC 4180 quoting.

### P2 — Invented fallback domains on invite and email links · new `lib/appUrl.ts`

Three call sites each invented their own fallback origin when `NEXT_PUBLIC_APP_URL` was
unset: `https://app.nimbus.io` (staff onboarding magic links) and `https://app.nautilus.io`
(transactional email links, webhook test payloads). **Neither is a domain we own.** In any
environment missing that variable, the app would mint invite and password-reset links
pointing at a stranger's domain — and nothing would error, so nobody would notice.

**Fixed:** one `appUrl()` resolver. Configured value → request origin → `localhost:3000`,
with a loud `console.error` in production when unset. No invented public hostname, because
there is no safe one.

### P3 — Copilot instructions were inert, and told you to use a library that isn't installed

`copilot-instructions.md` sat at the repo **root**. GitHub Copilot only reads
`.github/copilot-instructions.md`, so the file had no effect on the tool it exists for —
while its own first line said where it was supposed to live. Moved to `.github/`.

Its content had also drifted from the code in two ways that would actively mislead:

- **RBAC guidance was a version behind.** It said to gate writes on *role*, "mirroring the
  `app.has_org_role` policy". The codebase moved to granular permissions
  (`getActionContext()` → `ctx.can()`, enforced independently by `app.has_any_perm` in RLS).
  An AI following the old text would write exactly the bug fixed above in
  `applyForecastSettings`.
- **It recommended GSAP for motion.** GSAP is not a dependency and hasn't been — a comment
  in `globals.css` literally reads "(was gsap)". Following that advice adds a package the
  project deliberately dropped.

Rewritten: correct RBAC pattern, the `getActionContext()` rule, the no-invented-origin rule,
a data-access/performance section (hot vs cold paths, the RPC house pattern, why
`unstable_cache` isn't a fix for a slow query), a security-headers section with the two CSP
traps, and the three.js dynamic-import rule. Also corrected the blanket "no browser storage"
line, which the code contradicts in three places — `localStorage` is used for device-local
UI preferences, and that's fine; app state is what doesn't belong there.

### P3 — Remaining invented-origin fallbacks, and one that must stay

The five remaining `NEXT_PUBLIC_APP_URL ?? ""` sites (workspace creation, onboarding, bulk
invite, org invites, Stripe return URLs) now go through `appUrl()`.

The two Shopify OAuth routes deliberately **do not** — they read the env directly and 500
when it's missing. An OAuth `redirect_uri` must byte-match the one registered with Shopify,
so a request-origin fallback would either break the handshake or let a spoofed `Host` header
steer the redirect. Failing closed is correct there, and `lib/appUrl.ts` now says so, so
nobody "finishes the migration" later.

### P3 — Staff console branding

The staff console showed `NIMBUS` in its header, "Staff · Nimbus" as the page title, "All
organizations across Nimbus", and "already has a Nimbus account" in an error operators read —
against the README's own rule that Nautilus is canonical in user-facing copy and `nimbus`
survives only in internal identifiers. All corrected, including the `Logo` component's
accessible `title`. Internal identifiers (`app-nimbus` package, `nimbus-design-system.md`,
`nimbus-edge-functions`) intentionally unchanged.

### P2 — The Overview dashboard pulled whole tables to compute three aggregates

`lib/data/overview.ts` called `fetchAllPaged` three times on the app's **landing page**:

| Call | What it pulled | Now |
|---|---|---|
| `locations.quantity` | every active location row, to `SUM()` in JS | `app.overview_stock_total` |
| `scan_history.scanned_at` 14d | every scan in 14 days, to bucket by day in JS | `app.overview_scan_trend` |
| `products` + embedded locations | every product with `reorder_point > 0`, plus its locations | `app.overview_low_stock` |

`lib/data/paginate.ts` documents the rule this broke, in its own docstring: *"Use this for
COLD paths (reports, analytics)… For HOT read paths (ATP, dashboards) prefer an SQL-side
aggregate RPC."* At the 100k-row cap that was up to 100 sequential round trips per call.
`unstable_cache` softened it, but `OverviewRealtime` tag-busts that cache on every
`scan_history`/`locations` event — so the busier the warehouse, the more often the full
scan re-ran. It was a TTFB problem, and TTFB is the floor under LCP.

**Fixed** in `20260814120000_overview_aggregate_rpcs.sql`, following the
`analytics_aggregate_rpcs` house pattern (`security invoker`, `stable`, pinned
`search_path`, explicit grants). `bucketByDay` and the JS low-stock map/filter/sort/slice
are gone from `app/(app)/page.tsx`; the page now consumes finished values.

Semantics are a deliberate 1:1 port, verified against the live schema with read-only
queries before anything was written:

- **Low stock** — the `IN (sections of facility)` scoping was cross-checked against an
  independent join-based formulation of the same rule: identical `on_hand` on every row,
  correct deepest-shortfall ordering, and the `on_hand = reorder_point` boundary case
  included, matching the JS `<=`.
- **Trend** — day bucketing cross-checked against calendar-date differencing across a full
  14-bucket window: all 14 buckets identical. Uses the same
  `floor(epoch/86400)` arithmetic as the existing `daily_demand_series`, which is monotonic
  across DST, with the caller passing local midnight as the origin so buckets follow the
  operator's calendar rather than UTC.
- **Stock total** — matches the old filter workspace-wide and per-facility.

Two side fixes fell out: `lowStockCount` no longer falls back to `lowStock.length` (capped
at 6, so the KPI card read "6" for an org with fifty understocked SKUs whenever kiosk data
was unavailable), and the low-stock rollup index gap is closed — the only existing
`(org_id, product_id)` index on `locations` is partial `where quarantined`, the exact
complement of what this query reads, so it could never serve it.

**Migration applied** to `seypbrzjjiuibrwyxewj` on 2026-08-14 as remote version
`20260814174926 overview_aggregate_rpcs`. Post-apply verification:

- All three functions exist as `security invoker`, `stable`, `search_path=app, public`,
  granted to `authenticated` + `service_role` only — **not** `anon`, **not** `public`.
- Each called through the named-argument interface the code uses, returning the expected
  shape: `overview_low_stock` yields all seven columns with `category_name` resolved,
  correct deepest-shortfall ordering and `total_count` on every row; `overview_scan_trend`
  yields all 14 buckets; `overview_stock_total` matches workspace-wide and per-facility.
- `idx_locations_org_product_active` created with the intended partial predicate.
- Security advisors re-run: none of the three appear. Being `security invoker` keeps them
  off both SECURITY DEFINER lints.

> Local file is `20260814120000_overview_aggregate_rpcs.sql`; the remote version stamp
> differs because `apply_migration` assigns its own, which is already true of most
> migrations in this project (e.g. local `20260715120000` → remote `20260716011233`).

## Open — recommended, not applied

### P2 — Two different definitions of "low stock" on the same screen

Surfaced while porting the above. The Overview KPI card takes `lowStockCount` from
`getKioskData` → `app.inventory_list`, but the reorder-alerts panel directly beneath it
takes its rows from the overview path. The two disagree on what counts:

| | `inventory_list` (the card) | overview (the panel) |
|---|---|---|
| Locations with `section_id IS NULL` | always excluded (inner join on sections) | counted when workspace-wide |
| Quarantined units | **counted** | excluded |

So the card can say "7 low" above a panel built from a different rule. **This predates the
RPC work** — the old JS had the same split — and it was left alone deliberately, because
reconciling it changes a number on the dashboard and that should be a product decision, not
a side effect of a performance change. Worth picking one definition and moving both to it.

### P3 — `totalStock` counts quarantined units, low-stock doesn't

Same class of inconsistency, inside the overview path itself: the on-hand total includes
quarantined stock, while the low-stock rollup excludes it. Preserved 1:1 in
`overview_stock_total` rather than silently corrected, and flagged in the migration header.

### P3 — Staff console still branded "Nimbus"

`README.md` declares Nautilus canonical for all user-facing copy and `nimbus` acceptable
only in internal identifiers. The staff console is user-facing copy and shows `NIMBUS` in
the header (`app/admin/layout.tsx`) and "All organizations across Nimbus"
(`app/admin/page.tsx`). Cosmetic, staff-only, left alone to avoid churn on a surface no
customer sees — but it is inconsistent with the stated rule.

### P3 — Remaining empty-string origin fallbacks

Six call sites still use `process.env.NEXT_PUBLIC_APP_URL ?? ""`. These degrade to broken
relative links rather than pointing at an unowned domain, so they are much less dangerous
than what was fixed above — but they should move to `appUrl()` for consistency.

### P3 — Third-party logo CDN

`components/integrations/ProviderLogo.tsx` loads brand logos from `cdn.simpleicons.org` at
render. It's allowlisted in `img-src`, but it is a per-logo external request on the
integrations page and the logos break if the CDN is down. Vendoring the ~10 SVGs used would
remove the dependency and the requests.

## Verification

```bash
npm test        # 88 passed (12 files)
npm run build   # clean, 102 kB shared, no warnings
npx tsc --noEmit
```

The three new RPCs were validated as read-only queries against the live schema
(project `seypbrzjjiuibrwyxewj`) before the migration was written, then re-verified through
the real RPC interface after it was applied — see the cross-checks and the post-apply
checklist above.

**Caveat on that validation:** the dataset it ran against has no locations with a null
`section_id`, none inactive, and none quarantined, so the live data could not exercise the
edge cases where the old and new scoping rules could diverge. Those paths are correct by
construction and documented in the migration header, but they are unexercised by real rows.

CSP verified live against the dev server: all six headers served, login page renders with
zero console errors, pre-hydration theme script executes, both fonts load.

**Not verified:** authenticated pages under the new CSP. The preview renderer in this
environment wedges on authed routes, and no seeded credentials were available. The policy
is permissive on `script-src`/`style-src` and the only same-origin-restricted surfaces are
`connect-src` (Supabase https + wss, both allowlisted) and `img-src` (simpleicons
allowlisted), so the risk is low — but **a signed-in smoke test of Overview, a facility 3D
view, and one Realtime-backed page should be run before deploying.**
